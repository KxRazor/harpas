# Native plugin API

Scope: Harpas' own plugin API, how plugins written in different languages use it, and the two hosts that
run them: a WebAssembly host for most languages and the embedded JVM for Java. Bukkit/Paper compatibility is
a separate layer, covered in [jvm.md](jvm.md).

Status: design. Nothing here is implemented. Facts about toolchains and other projects cite their source in
[References](#references); everything else is a design decision of this project.

---

## Goals

| Goal | Meaning |
|---|---|
| **Many languages, one API** | The API is defined once; every language gets bindings generated from that definition |
| **Stability** | A plugin built against an API version keeps working when the server is updated |
| **Safety** | A plugin cannot crash the server or read memory it was not given |
| **Performance** | Compiled languages run close to native speed; calls across the boundary are few and coarse |

---

## Decisions

### 1. One API, defined in WIT

The API is described in **WIT** (WebAssembly Interface Types), in versioned packages
(`harpas:plugin@<version>`). WIT is the single source of truth:

- WASM plugins use bindings generated with WIT tooling for their language.
- Java plugins use Java bindings generated from the same WIT (decision 4).
- The Bukkit layer in [jvm.md](jvm.md) is an adapter on top of the same core API, not a parallel one.

### 2. WebAssembly components are the native plugin format

Plugins are WebAssembly components run by Wasmtime. Native shared libraries (`.so`, `.dll`) are **not**
supported as plugins:

| | WASM components | Native libraries |
|---|---|---|
| A plugin bug | Traps inside the sandbox; the server unloads the plugin | Can crash the whole server |
| Distribution | One `.wasm` for every OS and CPU | One build per OS and CPU |
| Server updates | Stable as long as the API version is supported | Must be rebuilt against each server build, since Rust has no stable ABI |
| Speed | Compiled to machine code by Wasmtime (Cranelift) | Native |

### 3. A synchronous base world, an asynchronous world on top

WASI 0.3, which moves async into the Component Model with `stream` and `future` types, was released on
June 11, 2026, and Wasmtime 46 is the first release implementing the final specification [1][2]. Toolchain
support for it is still partial: TinyGo offers only `wasip1` and `wasip2` targets [3], and other toolchains
list WASI 0.3 support as opt-in [6].

So the API has two worlds:

- **Base world (synchronous, WASI 0.2-compatible):** events, commands, world and entity access, scheduler.
  Every supported language can build against it from day one. Event handlers run inside the tick and return
  before the tick continues.
- **Async world (WASI 0.3):** the base world plus asynchronous I/O (HTTP, databases, files) for languages whose
  toolchains support it. Async work never blocks the tick; results come back as scheduled tasks.

The server hosts **several API versions at the same time**, one host per version, so an older plugin keeps
loading after an update.

### 4. Java plugins use the same API on the embedded JVM

There is no mature path from Java source to a WebAssembly component today: the existing Java-to-WebAssembly
compilers are experimental, and either keep WASI and Component Model support outside their main line or target
only browsers and Node.js. Instead:

- Java bindings are generated from the same WIT and run on the embedded JVM described in [jvm.md](jvm.md).
- A Java plugin is a `.jar` with a Harpas plugin manifest instead of `plugin.yml`. Its presence triggers the
  same on-demand runtime provisioning as a Bukkit plugin.
- Java plugins use the same bridge as the Bukkit layer (synchronous events, shared memory, interest masks), and the
  same event semantics as WASM plugins.
- Java plugins are **not sandboxed**: they run in the JVM with full access, like Bukkit plugins. This is stated
  clearly in the documentation for plugin authors and server owners.

### 5. Kotlin through Kotlin/Wasm, as an experiment

Kotlin plugins compile to WebAssembly components with Kotlin/Wasm's `wasmWasi` target. JetBrains publishes
an early prototype of Component Model support in Kotlin that works this way [4]:

- bindings generated by a Kotlin-enabled fork of `wit-bindgen`, built from source;
- the core module turned into a component with `wasm-tools` and the WASI preview 1 reactor adapter;
- a Gradle plugin of our own hides these steps (`./gradlew build` produces the `.wasm`).

Limitations to document for plugin authors:

- Kotlin/Wasm reached Beta with Kotlin 2.2.20 [5]; Component Model support is still evolving.
- Kotlin/Wasm does not run JVM bytecode, so **Java libraries cannot be used**, only Kotlin Multiplatform
  libraries that support Wasm. Database or HTTP access goes through APIs the server provides.

Kotlin authors who need Java libraries can use the Java host (decision 4), since Kotlin compiles to JVM
bytecode as well.

## Languages

| Language | How | Tier | Notes |
|---|---|---|---|
| Rust | `wasm32-wasip2` target, `wit-bindgen` [9] | First-class | Compiled; smallest and fastest |
| Go | TinyGo `wasip2` or componentize-go [3][6] | First-class | Compiled; the standard Go toolchain has no `wasip2` port yet [7] |
| TypeScript / JavaScript | jco + ComponentizeJS [9] | First-class | Embeds a JavaScript engine in each plugin, several megabytes *(measure)* |
| Python | componentize-py [9] | First-class | Embeds the whole CPython interpreter in each plugin [8] |
| Kotlin | Kotlin/Wasm (`wasmWasi`) [4] | First-class, **experimental** | No Java libraries (decision 5) |
| Java | Java bindings on the embedded JVM | First-class | Not sandboxed (decision 4) |
| C / C++ | `wit-bindgen`, `wasm-tools` [9] | Community | Compiled |
| C# | componentize-dotnet | Community | Status not verified |
| Zig, MoonBit | Component Model toolchains [9] | Community | Compiled |

First-class means: official SDK, project templates (`harpas plugin new --lang <language>`), documentation and
CI that builds a sample plugin for every API version.

Plugin authors are told plainly that languages embedding an interpreter (JavaScript, Python) cost several
megabytes of memory per plugin and run slower; they suit commands, administration and integrations better than
handlers for high-frequency events.

## API design rules

The same principles as the JVM bridge, adapted to WebAssembly, where every call across the boundary copies
its arguments and results:

- **Coarse calls.** One call per event, not one call per field.
- **Interest masks.** A plugin receives only the events it registered for; events with no listener in any
  plugin are never built.
- **Events by value.** An event is passed in, and the handler returns it; cancellation and modifications are
  read from the returned value.
- **Writes applied immediately.** A plugin's writes take effect at once, so later reads (by the same plugin or
  another) see them; only network output produced by plugin calls is batched with the tick's packets, as in
  [jvm.md](jvm.md#4-writes-applied-immediately-network-output-batched).
- **Handles for engine objects.** Players, entities and worlds are WIT resources (handles), not copies of their
  state.
- **No builder chaining in WIT.** Fluent APIs are provided by the language bindings, not by WIT methods that
  return the same resource, which would add boundary traffic. For Rust, `wit-bindgen` can generate chainable
  methods without changing the WIT [10].

## Edition-aware API

Part of the first API version (`harpas:plugin@0.1`):

- **Who the player is:** edition (Java or Bedrock), protocol version, and for Bedrock players the XUID
  ([identity.md](identity.md)).
- **Bedrock forms:** modal, simple and custom forms, and the server settings form, sent with Bedrock's form
  packets (`ModalFormRequestPacket`, `ServerSettingsRequestPacket`) [11].
- **Java dialogs:** the dialogs Java Edition supports since 1.21.6 (notice, confirmation, multi-action, server
  links and dialog lists, with text, checkbox, option and slider inputs) [12].
- Plugins choose per player; no automatic conversion between forms and dialogs is assumed.

## Sandbox and limits

- Memory limit per plugin.
- Epoch-based interruption, so a plugin stuck in a loop is stopped instead of freezing the tick.
- Capabilities (network, file system, other plugins) are declared in the plugin's metadata. A plugin gets
  exactly what it declares, **granted automatically**, and the granted capabilities are listed in the console
  when it loads. No configuration is needed; server owners who want to can restrict a plugin's capabilities in
  `harpas.toml`.
- A plugin that traps is unloaded and reported; the server keeps running.

---

## Packaging and lifecycle

- A plugin is a single `.wasm` component (or a `.jar` for Java) in `plugins/`, next to Bukkit/Paper jars.
- The component exports its metadata (name, version, API version, dependencies, capabilities), so no separate
  manifest file is needed for WASM plugins.
- Hot reload: a changed `.wasm` is reloaded without restarting the server.
- Plugin signing and a package registry are out of scope for the first API version; they will be designed
  once there is an ecosystem to serve.

## Threading

The engine runs the game in vanilla tick order on one logic thread ([engine-core.md](engine-core.md)). Native
plugins follow the same model as Bukkit plugins in [jvm.md](jvm.md#threading):

- Event handlers run **synchronously on the logic thread, at the point of the tick where the event happens**.
  A cancellable event is decided before the action happens.
- Scheduled tasks run on the logic thread at fixed points of the tick.
- Asynchronous work (I/O in the async world) runs off the logic thread and delivers results as scheduled tasks.

Running plugins per region in parallel was considered and set aside, because the engine keeps vanilla's tick
order rather than ticking regions in parallel.

In modded mode the same rules apply on the modded server's main thread instead of the Rust logic thread
([mod-support.md](mod-support.md#plugins-and-mods-together)).

---

## Java bindings

The Java bindings are produced by **our own WIT-to-Java generator**. It is built for the JVM bridge in
[jvm.md](jvm.md): engine objects map to the bridge's stable Java objects, reads come from the shared memory
views, and writes are downcalls applied immediately. A general-purpose generator would not know about that bridge.

## Validation

1. **Hello world per language:** every first-class language builds and loads a sample plugin in CI.
2. **Event overhead:** cost per dispatched event and per host call, per language, with 200 simulated players.
3. **Memory per plugin:** resident memory of one loaded plugin per language, to back the documented costs of
   JavaScript and Python.
4. **Isolation:** a plugin that traps, loops forever or exceeds its memory limit is stopped without affecting
   the server.
5. **Version coexistence:** plugins built against two API versions run on the same server.
